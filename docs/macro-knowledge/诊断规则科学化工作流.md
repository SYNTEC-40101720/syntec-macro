# 诊断规则科学化工作流

> v4.0.0+ 起，新增或修改诊断规则必须按本工作流推进；CI 与发布门禁以 `scripts/checkDiagnosticGovernance.js` 守卫。
> 主入口：`docs/迭代优化计划.md` §4。

## 背景

诊断规则从 v2.13 ~ v3.1.0 由 JS analyzer + Rust analyzer 双路径并行实现与维护。v4.0.0 R1.2 Stage B 退役 JS analyzer 后，Rust/Wasm 成为唯一分析后端，但 `src/diagnosticCodes.js` 与 `src/diagnosticActions.js` 仍是 host/worker 共享的诊断元数据真源（hover、codeAction、文档派生都依赖这两张表）。

为了在「Rust 唯一 emit 路径 + JS 仍是元数据真源」的混合架构下保持规则的可追溯性，把"新增一条诊断规则"流程化做"四件套登记 + 工具守卫"，避免出现：Rust 端 emit 了新 code 但 JS `diagnosticCodes.js` 没注册（host 看不到 hover/QuickFix）、或 JS 注册了新 code 但 parity 清单/能力矩阵未登记（边界漂移）、或两端都改了但派生文档没同步。

## 四件套登记点

每一个稳定 `SYNTEC_*` 诊断 code 必须在 4 个登记点同步落地：

| 登记 | 文件 | 角色 | 校验粒度 |
|---|---|---|---|
| (1) JS 注册 | `src/diagnosticCodes.js` | host/worker 共享 DiagnosticCode 枚举 | HARD（缺则 fail） |
| (2) Rust emit | `crates/syntec-core/src/lib.rs` | 唯一 emit 入口 Literal | HARD |
| (3) parity 交叉引用 | `docs/Rust诊断parity清单.md` §「诊断 code ↔ 能力矩阵交叉引用」 | code → 能力 ID 映射 | HARD |
| (4) 用户文案 | `src/diagnosticActions.js` `DIAGNOSTIC_HELP[code]` | hover/CodeAction 显示文案 (派生层 `docs/诊断规则与修复动作.md` 由此生成) | SOFT（缺则 warning） |

> 能力矩阵 [`docs/macro-knowledge/MACRO能力矩阵.md`](MACRO能力矩阵.md) 通过能力 ID 间接登记所有 code：parity 清单 §交叉引用表是唯一"code → 能力 ID"指针，能力矩阵本身只承载能力级状态（已核实/部分核实/待审计/不做静态判断），不重复登记 code literal。

## 治理脚本

`scripts/checkDiagnosticGovernance.js` + npm `check:diagnostic-governance`：

```powershell
# review 模式 (默认): HARD 缺口阻塞, SOFT 缺口只 warning
npm run check:diagnostic-governance

# --strict 模式: SOFT 缺口也算 FAIL (用于发布收口)
npm run check:diagnostic-governance -- --strict

# --report 模式: 输出 markdown 报告 (适合 append 到文档或 PR 描述)
npm run check:diagnostic-governance -- --report
```

校验逻辑：
1. 扫 `src/diagnosticCodes.js` 提取全量 `KEY: 'SYNTEC_*'` 注册项（兼容末项无尾逗号）。
2. 扫 `crates/syntec-core/src/lib.rs` 提取 `"SYNTEC_*"` literal 集合（排除 `SYNTEC_CORE_*` ABI 符号）。
3. 扫 `docs/Rust诊断parity清单.md` 提取 `` `SYNTEC_*` `` 反引号登记。
4. `require('src/diagnosticActions.js')` 取 `DIAGNOSTIC_HELP` key 集合。
5. JS 侧每个 code 必须在 (1)+(2)+(3) 全 PASS，缺一项即 HARD fail。Rust literal 不在 JS 注册表也作 HARD fail（反向守卫）。
6. (4) 缺 HELP 文案仅 SOFT warning（不阻塞）。

## CI 接入

- `.github/workflows/ci.yml`: PR 阶段 `npm run check:diagnostic-governance` 作 informational review (`continue-on-error: true`)，HARD 缺口仅在 actions log 显示 warning。
- `.github/workflows/release.yml`: 发布收口跑 `npm run check:diagnostic-governance` 默认模式（HARD 阻塞），SOFT 缺口暂不阻塞；待 SOFT 全部补齐后再把命令升为 `-- --strict` 作发布硬门禁。

> 单元测试 `tests/checkDiagnosticGovernance.test.js` 12 项契约已挂到 `npm test`，覆盖：JS regex 兼容末项无尾逗号、Rust 排除 CORE ABI、parity 文档反引号登记、`buildChecks` 默认 vs strict 数量一致、JS==Rust==parity doc、`formatResult` markdown 含关键段等。

## 新增诊断规则工作流（agent / user 必走步骤）

```
1. 规范手册与能力矩阵对齐
   - 在 docs/新代MACRO语法规范手册.md 或对应子文档登记新规则的语法 spec
   - 在 docs/macro-knowledge/MACRO能力矩阵.md 找到/新增能力 ID (例如 FMT-002)
     并标注状态 (已核实 / 部分核实 / 待审计 / 不做静态判断)

2. JS 注册 DiagnosticCode (元数据真源)
   - 在 src/diagnosticCodes.js 加 KEY: 'SYNTEC_NEW_CODE_NAME',
   - 在 src/diagnosticActions.js 加 DIAGNOSTIC_HELP['SYNTEC_NEW_CODE_NAME'] =
     { title: '短文案', message: '详细说明, 含改写方向、影响范围、控制器版本门槛' }
   - 若有 QuickFix 或机械替换, 在同一文件加 DIAGNOSTIC_REPLACEMENTS['SYNTEC_NEW_CODE_NAME']

3. Rust emit 入口
   - 在 crates/syntec-core/src/lib.rs 适当 validator (line/robot/function/control_flow)
     中 push_diagnostic 时使用 "SYNTEC_NEW_CODE_NAME" literal
   - 复用 matches_keyword / is_identifier_character / utf16_prefix_len 等 helper
     保持与既有 implementation 一致; 跨行状态机放 RobotLineState

4. parity 清单交叉引用
   - 在 docs/Rust诊断parity清单.md §「已覆盖」加 `SYNTEC_NEW_CODE_NAME` 项
   - 在 §「诊断 code ↔ 能力矩阵交叉引用」表加一行: `SYNTEC_NEW_CODE_NAME` | 新能力 ID | 主题
   - 顶部状态栏 marker (例如 68/68 → 69/69) 同步

5. 差分样例与单测
   - 在 scripts/compareRustCore.js 的 CASES 数组追加正反例
     (符合 push_diagnostic 的输入 / 期望 line/col/endCol/severity/code 序列)
   - 若规则复杂, 在 lib.rs 内或 tests/checkDiagnosticGovernance.test.js 加单测

6. 派生文档刷新
   - 运行 npm run docs:diagnostics 重生成 docs/诊断规则与修复动作.md
     (从 diagnosticCodes.js + diagnosticActions.js 派生)
   - 若 docs:diagnostics:check FAIL 说明派生层未同步, 不能提交

7. 全量门禁
   - npm run check:diagnostic-governance (期望 HARD=0; SOFT=N, N+1 是当前 已知缺口)
   - npm test / npm run lint / npm run typecheck:analysis
   - npm run compare:rust (若修改 Rust 端 emit 行为)
   - npm run check:release:readiness --strict
   - 必要时 npm run probe:rust:wasm / benchmark:rust:wasm (若 wasm 重打包)

8. CHANGELOG 记录
   - 在 [Unreleased]/Added (或 Changed) 段记 4 行:
     - 规则名称 + 用途
     - JS DiagnosticCode 注册 + DIAGNOSTIC_HELP 文案
     - Rust emit 入口 + compare:rust 差分样例编号
     - parity 清单 marker 更新 (如 69/69)
     - 能力矩阵状态变更 (如 FMT-001 已核实 → 已核实 + 实测边界)
```

## 例外：完全不引入新 code 的改动

如果只是调语义/提示文案/位置范围而不新增 `SYNTEC_*` code，最少只需：
1. JS 修改 `diagnosticActions.js` `DIAGNOSTIC_HELP` 或 `DIAGNOSTIC_REPLACEMENTS` 文案；
2. Rust 端 `lib.rs` 修改 push_diagnostic 的 message 或位置参数；
3. `npm run docs:diagnostics` 重生成派生文档；
4. `npm run compare:rust` 确认 parity 没破。

## 已知 SOFT 缺口（截至 2026-09-22）

27 个稳定 code 当前缺 `DIAGNOSTIC_HELP` 文案（`docs/诊断规则与修复动作.md` 派生层 fallback 为 `-`），由 `check:diagnostic-governance` SOFT warning 列出：

- `SYNTEC_MISSING_SEMICOLON` / `SYNTEC_CONTROL_STRUCTURE_TRAILING_SEMICOLON`
- `SYNTEC_UNSUPPORTED_ELSIF` / `SYNTEC_UNSUPPORTED_DEFAULT` / `SYNTEC_UNSUPPORTED_DIV` / `SYNTEC_UNSUPPORTED_*_OPERATOR`（7 项）/ `SYNTEC_UNSUPPORTED_COMPOUND_ASSIGNMENT` / `SYNTEC_UNSUPPORTED_INCREMENT` / `SYNTEC_UNSUPPORTED_FANUC_COMPARISON`
- `SYNTEC_CONTROL_UNMATCHED_*`（5 项）/ `SYNTEC_CONTROL_ELSEIF_AFTER_ELSE` / `SYNTEC_CONTROL_UNCLOSED_BLOCK`
- `SYNTEC_ASSIGNMENT_STYLE_EQUALS`
- `SYNTEC_ROBOT_DEPRECATED_MOVJ_II` / `SYNTEC_ROBOT_DIRECT_ARG_EQUALS` / `SYNTEC_ROBOT_TOOLCOR_*`（3 项）

这些 code 大多有 `DIAGNOSTIC_REPLACEMENTS` 或硬编码 QuickFix 标题（`scripts/generateDiagnosticDocs.js` `quickFixFor` 已 hardcode fallback），所以用户在 CodeAction 仍能看见 QuickFix，但 hover/info 上的"说明"段目前 fall back 到 `-`。补齐优先级 P2，由 user 单独批量推进；脚本 `--report` 模式可输出完整缺口清单供参考。

## 关键经验

- **JS 注册表是元数据真源，Rust 是 emit 真源**：v4.0.0 后 JS analyzer 退役了，但 `src/diagnosticCodes.js` 与 `src/diagnosticActions.js` 依然是 host/worker 共享的元数据真源（hover、codeAction、docs 派生、测试断言）。任何新 code 必须先在 JS 注册，再在 Rust emit。
- **能力矩阵不重复登记 code literal**：能力矩阵只承载能力级状态；code → 能力 ID 的指针由 parity 清单 §交叉引用表单向承载，避免双源真相。
- **regex 兼容末项无尾逗号**：`src/diagnosticCodes.js` 的最后一个 key 无尾逗号，扫注册项的 regex 必须用 `,\s*$` 可选匹配 + `$` 行尾锚定，否则会漏掉末项（本次实测漏掉 `SYNTEC_ROBOT_G10_L1802_SILENT_VERSION_GATE` 触发假 HARD）。
- **HARD=SOFT=0 升 strict 时机**：当 SOFT 全部补齐（27 → 0）后，可把 `.github/workflows/release.yml` 中 `npm run check:diagnostic-governance` 升为 `-- --strict` 作发布硬门禁。在此之前只能用默认模式（HARD 阻塞 SOFT informational）。
- **不要把运行时差异塞进静态诊断**：能力矩阵「不做静态判断」状态的规则只走 hover / 文档，不进 validator。规范手册有明确文本 + 跨版本稳定 + 误报成本低时才进 emit。
